# 寫功能規格

規格是寫測試和程式的依據，使用者確認之前，hook 會擋下 `src/`、`e2e/`、`public/` 的修改。這個 skill 的目標是：使用者確認規格的時候，該決定的事都已經問過，不要等到審查或實作時才發現。

這個 skill 改寫自後端的同名 skill。後端階段 2 的經驗是：使用者很難從一份長文件裡發現「這裡漏了什麼」，但回答一個明確的問題只要幾秒。所以重點有兩個：

1. 自己把規則想完整。每個畫面在載入中、沒有資料、出錯時顯示什麼，表單怎麼檢查，這些是寫規格的人該想到的，不該靠使用者挑出來
2. 只有使用者能決定的事，整理成明確的選擇題來問

## 開始之前

- 照 CLAUDE.md 的 Git 流程，在 `feature/<簡短描述>` branch 上做。規格檔是 `docs/specs/<branch 名稱去掉 feature/>.md`
- 規格的狀態（草稿 → 已確認 → 已完成）和 hook 的行為，見 CLAUDE.md 和 `docs/specs/README.md`

## 步驟

### 1. 讀資料

- `docs/plan.md`：這個階段的項目和完成標準、第 1 節決策紀錄、第 4 節頁面與路由、第 5 節設計原則、第 6 節需要後端定下來的事，以及這個階段底下之前審查時延後處理的項目
- `docs/adr/README.md` 裡和這次有關的 ADR
- `docs/specs/README.md` 裡已完成的規格：這次會不會改變它們的行為
- 後端的資料（路徑見 CLAUDE.md）：`docs/plan.md` 的功能規格、對應階段的後端規格（`docs/specs/`），以及實際的 API。後端啟動時可以讀 `http://localhost:5034/openapi/v1.json`；沒有啟動就讀後端的 controller 和 DTO。**以後端實際的行為為準**，plan 的 API 草稿可能已經改了
- 現有的前端程式：共用元件、service、pipe。規格要建立在現有的結構上，要改的話寫清楚

### 2. 寫草稿

從 `docs/specs/_template.md` 複製，加進 `docs/specs/README.md` 的清單，狀態「草稿」。寫的時候用下面的「檢查清單」逐項想過。

### 3. 問使用者

把「待確認」的問題用選擇題問使用者（見「怎麼問」），同時寫在規格的「待確認」段落，使用者之後看規格時也看得到。

### 4. 寫回結論，請使用者確認

- 使用者回答後，把結論寫進規格對應的段落，從「待確認」移除。理由寫在決定旁邊，之後的人才知道為什麼這樣決定
- 決定和 plan 不同時，一併更新 plan，並在規格寫「和 plan 不同的地方」；重要的決定另外寫 ADR
- 全部寫好後，請使用者看過整份規格。使用者同意後，把狀態改成「已確認」（會跳出確認視窗）。在這之前不寫測試和程式

### 5. 確認之後還要修改時

確認之後的每次修改都會跳出確認視窗，所以把要改的地方整理好，一次改完。會改變已完成規格的行為時，寫在「影響到的既有規格」。

## 檢查清單

### 從 plan、ADR 沿用的決定

plan 是專案剛開始時寫的，很多細節要到寫規格時才看得到。沿用 plan 或 ADR 的決定時，挑出「之後很難改」的，明確問使用者要沿用還是要改，例如：

- 資料存在哪裡、存多久，例如 token、購物車
- 權限和導向的規則，例如沒登入、角色不對、需要改密碼時去哪一頁
- 範圍裡的某個功能還要不要做

之後容易改的，例如顯示的文字、按鈕位置、排序方式，不用問，直接決定寫進規格。

### 後端的 API

- 這次用到哪些 API，請求和回應的欄位以後端實際的為準
- 後端還沒有、或格式不好用的：不要在前端繞過去。寫在規格的「需要後端配合」，並記在 `docs/plan.md` 第 6 節，問使用者要先改後端，還是這次先不做
- 每支 API 會回哪些錯誤（400 的欄位錯誤、401、403、404、409 之類），每種錯誤在畫面上怎麼顯示

### 每個畫面

- 誰可以進來：沒登入、角色不對、需要改密碼時導向哪裡
- 載入中、沒有資料、載入失敗時分別顯示什麼
- 網址要帶哪些狀態，例如搜尋關鍵字、分頁、篩選條件；重新整理或分享網址時要不要保留
- 操作成功後去哪裡、顯示什麼

### 每個表單

- 必填、格式、長度：前端先檢查哪些。規則要和後端一致，以後端為準
- 後端回的欄位錯誤顯示在哪個欄位，不是欄位的錯誤顯示在哪裡
- 送出中鎖住按鈕，避免重複送出
- 離開還沒存的表單要不要提醒

### 顯示

- 金額、時間、狀態用 `shared/` 的 pipe（見 `docs/plan.md` 5.4），不在規格裡另外訂格式
- 停用、下架的資料要不要顯示、怎麼標示

### 寫行為，不寫實作

- 規格寫「使用者看到什麼、能做什麼」，不寫「用哪個元件、signal 怎麼設計」。元件的拆法、狀態管理的方式在實作時決定
- 測試怎麼寫（例如用什麼假資料）不寫進規格

## 驗收條件

- 寫真正重要的行為：權限與導向、送出的資料正確、使用者看得到的結果、出錯時的顯示。實作細節不寫成驗收條件：每一條都要寫測試、之後一直維護，寫得太細，審查也能一直挑下去（見後端 ADR-0017）
- 每一條都要能寫成測試，並寫明用哪一種：
  - **元件測試**（Vitest）：畫面顯示、表單檢查、送出的請求內容、各種錯誤回應的顯示。用 `HttpTestingController` 模擬後端
  - **E2E 測試**（Playwright）：需要真的後端才能確認的完整流程，例如登入後一路下單到完成。E2E 比較慢，只用在重要流程
- 「預期結果」要具體到測試能直接檢查，例如顯示哪段文字、導向哪個網址、送出的請求帶了哪些欄位
- 同一條規則的正反兩面放在同一條，例如「經銷商看得到自己的訂單；網址改成別人的訂單 id 會顯示找不到」
- 編號從 AC-1 開始

## 怎麼問

- 用 AskUserQuestion 問：一次最多 4 題、每題 2–4 個選項。建議的選項放第一個，標「（建議）」；每個選項的說明寫理由，以及選了之後會怎樣。題目多時分幾次問。畫面的版面可以用 `preview` 放 ASCII 示意圖
- 只問使用者才能決定的事：業務規則、要不要做、要不要沿用 plan 的決定、明顯影響使用方式的畫面流程。技術上的選擇自己決定，理由寫在規格裡，使用者確認規格時看得到；只有影響很大、或兩種做法各有明顯代價的才問
- 規格的「待確認」段落寫同樣的題目，每題附上建議和理由

- 共用的規則集中寫一次
- 表格下面用一段話說明為什麼這樣決定
- 規格和 plan 不同時，寫在「和 plan 不同的地方」
